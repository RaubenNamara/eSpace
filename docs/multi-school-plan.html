eSpace for many schools

How eSpace becomes one system that many schools use - each with its own space, all sharing the content that St Mark's built.

Prepared 5 October 2026 · For the eSpace team · Status: agreed direction, to be built after the current round of improvements

1. In short

  • One system, many schools. Every school uses the same eSpace, at its own web address (for example stmark.<espace-domain>, kings.<espace-domain>).
  • Each school is separate. Every school has its own database: its students, teachers, marks, chats and reports are never visible to another school.
  • St Mark's is the master school. Its teaching content - curriculum, eNotes, eLibrary, Item Bank, Virtual Lab - is the master copy. It also stays our test school: new features go to St Mark's first.
  • New schools start with St Mark's content. Their teachers can read it and edit it. Edits stay in their school only; the master at St Mark's never changes.
  • Master updates flow out. When St Mark's improves a topic, schools that have not edited it get the new version automatically; schools that edited it are told and can choose.
  • A developer console - only for the eSpace team - to enrol, import, suspend and delete schools, and update them all at once.

2. Decisions already made

Rejected: one shared database with a school column on every table (too risky - one missed filter shows another school's students); a separate copy of the code per school (every update deployed many times).

How do schools get the content?Copied into each school when it is enrolled, and kept in step by a sync (section 5). Not read live from St Mark's: if St Mark's deletes something, other schools keep theirs, and each school stays fast and independent.
What is never shared?Anything about people: students, teachers' accounts, marks and submissions, Learning Maps, chats, notices, parent links, report cards, logs.

3. To settle before we build

  1. Content agreement with St Mark's. Most master content was written by St Mark's teachers, and St Mark's is a client. Agree in writing that content made on eSpace may be shared with other eSpace schools - for example with credit ("Notes by St Mark's College", shown automatically) and/or a discount for St Mark's.
  2. The domain name - buy it, and set a wildcard subdomain (*.<domain>) pointing to the eSpace folder.
  3. Hosting - check how many databases the hosting plan allows, and create a cPanel API token so the console can create a school's database by itself. (Without a token: create each database by hand in cPanel and paste its name into the console.)
  4. Pricing - price per learner per term (already on the website), trial length, and what happens when a school stops paying (suspend after N days).
  5. Email for the platform - an address for school-admin invitations and the weekly parent digest across all schools.

4. How it works - architecture

4.1 Finding the school

  • Every request looks at the web address: kings.<domain> → school "kings" → its database.
  • A small platform database holds the list of schools and how to reach each one's database. It holds no student data.
  • The main website (<domain>, no subdomain) shows the public landing site and the guide, as now.
  • Locally we test with stmark.localhost and demo.localhost - no domain needed to build it.

4.2 What changes in the code

AreaChange
Database connectionChosen per request from the school's record, instead of one fixed database in .env.
Uploaded filesEach school's uploads in its own folder: uploads/<school>/.... Shared master files (book PDFs, images in notes) referenced, not copied, where possible to save space.
Sign-inSessions tied to the school's subdomain, so a login at one school never works at another.
School name, crest, coloursAlready per school (school_settings) - just lives in each school's database.
Scheduled jobsThe weekly parent digest (and future jobs) runs once for every active school.
Everything elseUnchanged: every page keeps working as it does today, because each school's database looks exactly like St Mark's.

5. Shared content - copy and keep in step

5.1 What is shared

Shared from St Mark's (content)
  • Curriculum: topics, learning outcomes, competencies, constructs
  • eNotes: topics, pages, narration, images
  • eLibrary books and Item Bank papers
  • Videos (links / files)
  • Virtual Lab experiments and templates
  • Question bank and AOI scenarios (optional)
Never shared (people and results)
  • Students, teachers, HODs, admins
  • Submissions, marks, Learning Maps, report cards
  • Chats, notices, parent links, notifications
  • Reading progress, notes, highlights
  • Logs and settings

5.2 How each copied item is tracked

Every shared content row in a school's database gets four small fields:

FieldMeaning
master_idThe item's id at St Mark's (empty for the school's own new items).
master_versionWhich version of the master this copy is based on.
edited_locallySet the first time a teacher at this school changes the item.
source_credit"St Mark's College Namagoma" - shown on the item if agreed (section 3).

5.3 What happens when ...

EventResult
A school is enrolledIt receives a copy of the master content packs we choose (all, or by subject / class level).
A teacher at another school edits a noteTheir copy becomes "edited locally". St Mark's master is untouched. Other schools are untouched.
A school adds its own new noteIt is theirs only (no master_id).
St Mark's improves a master itemIts version goes up. At the next sync, schools that have not edited it get the new version automatically.
... and a school had edited itThey keep their version and see a notice: "St Mark's updated this topic - compare / switch to the new version / keep mine".
St Mark's deletes a master itemOther schools keep their copy (it simply stops receiving updates).
Sync runsFrom the console ("Push master updates"), or on a schedule. Each run is logged.

6. The developer console

A separate area, only for the eSpace team, at console.<domain>.

ScreenWhat it does
SchoolsEvery school: status, learners, teachers, storage used, last activity, plan. Search and filter.
Enrol a schoolName, subdomain, crest, colours, first admin's name and email, plan. Creates the database from the template, runs all migrations, copies the chosen content packs, creates the admin account, sends the invitation.
School pageDetails, usage, the content it has edited, its migration status; actions: open as support (logged), suspend / reactivate, delete.
SuspendBlocks sign-in with a friendly message; keeps all data.
DeleteTakes and downloads a full backup first, asks for the school's name to be typed, then removes the database and files. Logged.
Update all schoolsRuns new database migrations on every school, one by one, with a dry run first and a result per school.
Master contentWhat St Mark's has changed since the last push; push to all schools or chosen ones.
Usage and billingLearners per school per term, for invoicing; trial end dates; overdue schools.
TeamConsole accounts for the four of us, and the audit log.

7. Onboarding a new school

  1. Enrol in the console (section 6) - the school's space exists within minutes.
  2. Set up the year: academic year, terms, departments, subjects (pre-filled from St Mark's, editable).
  3. Classes and streams in bulk: e.g. S.1-S.6 × East / West / North in one step.
  4. Import staff from Excel/CSV: name, email/phone, department, role (teacher / HOD), subjects. Preview with errors highlighted before saving; logins created.
  5. Import students from Excel/CSV: name, admission number, class, stream, gender. Preview, then save; usernames and first passwords created and printable as login slips.
  6. Assign teachers to classes and subjects.
  7. Check and hand over: a checklist page confirms each step, then the school admin takes over. Training follows module by module.

9. Safeguards

  • Isolation tests: automated checks that a login, link or file from one school never opens another school's data.
  • Backups: every school backed up on a schedule; always before a delete or a migration run.
  • Migrations: dry run first; run school by school; stop and report on the first failure; never leave a school half-updated.
  • Support access: the team can open a school only through the console, and every visit is logged.
  • Content sync: never overwrites a school's local edits; every push logged and reversible for unedited items.
  • Performance: each school is its own database, so one busy school does not slow the others; watch total server load as schools grow.
